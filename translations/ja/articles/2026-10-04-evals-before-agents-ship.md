数か月前、私は Amazon の決済部門にあるエージェントプラットフォームチームに加わりました。私たちは他チームの AI エージェントをホストしています。エージェントはチケットを解決し、コメントを追加し、インシデントをトリアージします。

最近、あるエージェントに一つの変更を出荷する必要がありました。新しいシステムプロンプト、新しいスキル、より新しいモデル、そして思考モード（thinking mode）の有効化です。問いはシンプルで、新しいエージェントは**良くなったのか、悪くなったのか**です。しかし、それに体系的に答える方法がありませんでした。そこで直近のチケットを 50 件手作業で集め、両方のバージョンを実行し、それぞれが投稿した内容を LLM を審査役（judge）にしてチケットごとに比較しました。この一つの変更を昇格させるのに約一週間かかり、しかもその作業は次のエージェントには何一つ再利用できませんでした。

ここにギャップがあります。私たちがホストするすべてのエージェントに対してスケールする評価フレームワークが、まだ存在しないのです。そこで、業界がどのように取り組んでいるかを調べました。この記事は、私たちが構築したいと考えているフレームワークについて、なぜ、何を、どのようにの三点から説明するものです。

## なぜ：判断はユニットテストできない

エージェントの失敗の大半は、私たちのコードではなくモデルの判断にあります。誤ったツールを選ぶ、誤った引数を渡す、早すぎる段階で止まる、投稿すべきでないものを投稿する、といったものです。これを捉えにくくしている要因が三つあります。

- **エージェントは非決定的です。** 一回うまくいったところで、ほとんど何も証明できません。τ-bench では、最良の function calling エージェントでもタスクの半分未満しか解けず、リテール領域で同じタスクを 8 回試してすべて成功する割合は 25% 未満でした [[1]](#ref-1)。
- **足元のすべてが変化します。** モデルのバージョン、プロンプト、スキル、ツールのスキーマはどれも変わり続け、そのいずれもがコードを変更することなく振る舞いを変えてしまいます。
- **オブザーバビリティは評価ではありません。** LangChain が 1,340 人の実務者を対象に行った 2026 年の調査では、89% がエージェントのオブザーバビリティ（observability）を整備していましたが、オフライン評価を実施していたのは 52.4%、オンライン評価は 37.3% にとどまりました [[2]](#ref-2)。トレースは何が起きたかを教えてくれますが、それが正しかったかを教えてくれるのは評価です。

評価がないと、チームは後手に回るループに陥ります。問題は本番で表面化し、一つを直すと別の何かが壊れます [[3]](#ref-3)。私の 50 チケットの一週間は、まさにそのループを手作業でこなしたものでした。

## 何を：用語の整理

Anthropic のエージェント評価ガイドは、便利な共通言語を提供しています [[3]](#ref-3)。

| 用語 | 意味 |
|---|---|
| タスク（Task） | 一つのテストケース。入力と成功基準の組み合わせです |
| 試行（Trial） | タスクに対する一回の試み。結果はばらつくので複数回実行します |
| 採点者（Grader） | 試行を採点するもの。コード、モデル、または人間です |
| トランスクリプト（Transcript） | 実行の完全な記録。メッセージ、ツール呼び出し、推論を含みます |
| 結果（Outcome） | 返答だけでなく、最終的な世界の状態です |

重要なスイートは二種類あります。**リグレッション評価（regression evals）**は、エージェントが以前できていたことを今もできているかを確認するもので、100% 近くを維持すべきです。**ケイパビリティ評価（capability evals）**は、まだできないことを測るもので、低いスコアから始まるのが自然です。

そして評価を実行する場所も二つあります。リリース前に固定データセットに対して実行する**オフライン**と、リリース後に実際のトラフィックに対して実行する**オンライン**です。オフラインはリリースのゲートとなり、オンラインはその後に起きることを監視します。

## どのように（前編）：リリース前

ここでのすべては**ゴールデンセット（golden set）**、つまり良い結果がわかっている実際のタスクに対して実行します。数百件の架空のタスクではなく、実際のチケットや実際の失敗から集めた 20〜50 件のタスクから始めましょう [[3]](#ref-3)。何もしないことが正解となるケースも含めてください。

| チェック | 何に答えるか |
|---|---|
| リグレッションゲート | モデル、プロンプト、スキル、ツールを変更した後も、すべてのゴールデンタスクが通るか。変更のたびに CI で実行します。 |
| 品質チェック | 曖昧な 1〜5 のスコアではなく、特定の振る舞いに対する合否（「人間にエスカレーションしたか？」）で判定します [[4]](#ref-4)。 |
| 軌跡（trajectory）の採点 | 正しいツールを、正しい引数で選び、ポリシーに従ったか [[5]](#ref-5)。 |
| 結果チェック | 最終状態は正しいか。副作用の重複はないか。 |
| 繰り返し試行 | 各タスクを k 回実行します。k 回の試行が*すべて*成功する確率である pass^k は、運ではなく信頼性を測ります [[1]](#ref-1)、[[3]](#ref-3)。 |
| 安全性ケース | プロンプトインジェクションや、ポリシーに違反するツール呼び出し。 |
| 予算 | タスクごとのコストとレイテンシ。正しい答えでも 3 分かかるなら失敗になりえます。 |

曖昧な部分には LLM ジャッジ（LLM judge）を使って構いませんが、それは人間のラベルと照らし合わせて検証した後に限ります。ジャッジと専門家の判断が食い違うなら、そのスコアには意味がありません [[4]](#ref-4)。

これが整えば、私の 50 チケットの一週間はコマンド一つになります。旧エージェントと新エージェントでゴールデンセットを実行し、比較するだけです。

## どのように（後編）：リリース後

ゴールデンセットは現実の代理にすぎません。実際のトラフィックには、必ずそこに含まれていない何かがあります。

**まずはシャドーモード（shadow mode）から。** 新しいエージェントを本番エージェントと同じライブチケットに対して並行して実行しますが、その出力は決して表に出しません。オフラインで使ったのと同じチェック、つまり同じ結果、同じツール、同じジャッジで両者を比較します。シャドーイングには二本目のパイプラインというコストがかかりますが、ユーザーが悪い回答を目にすることはありません。

そのうえで、段階的にロールアウトします。

- **カナリアリリース（canary）。** トラフィックのごく一部、たとえば 5〜10% を新しいエージェントに流し、メトリクスが維持されている間だけ割合を広げます。
- **オンライン評価。** 本番トランスクリプトのサンプルを同じ採点者で非同期に採点し、品質が落ちたらアラートを出します。
- **実際のシグナル。** 人間へのエスカレーション、再オープンされたチケット、ユーザーフィードバックはノイズが多いものの、これこそが正解データ（ground truth）です。
- **トランスクリプトを読む。** 人間による定期的な確認は採点者が見逃したものを拾い、採点者自体の正しさも保ちます。

単一のレイヤーですべてを捉えることはできません。Anthropic はこの組み合わせをスイスチーズモデル（Swiss cheese model）と呼んでいます。各レイヤーには穴がありますが、重ねることで、すり抜ける失敗はわずかになります [[3]](#ref-3)。

## フライホイール

最も重要な矢印は逆向きを指しています。シャドー、カナリア、本番で見つかったすべての失敗は、新しいゴールデンタスクになります。時間が経つにつれ、リグレッションスイートは想像上の失敗ではなく実際の失敗から育ち、昇格のたびにコストが下がっていきます。

プラットフォームチームにとって、これこそが本当の見返りです。共有のハーネス、エージェントごとのゴールデンセット、そして標準化された昇格パスがあれば、「エージェントを段階的に引き上げる」作業は一週間の手作業から、ホストするすべてのエージェントが使えるパイプラインへと変わります。

## チェックリスト

- エージェントごとに、「何もしない」ケースを含む 20〜50 件の実際のタスクでゴールデンセットを作り始める。
- モデル、プロンプト、スキル、ツールのすべての変更を、CI のリグレッション評価でゲートする。
- 最終的なテキストだけでなく、結果と軌跡を採点する。合否形式のチェックを優先する。
- LLM ジャッジは人間のラベルで較正する。
- タスクは複数回実行し、pass^k を追跡する。
- カナリアの前にシャドー、全面ロールアウトの前にカナリアを行う。
- 本番での失敗はすべてゴールデンタスクにする。

## あなたへの問い

あなたのチームでは、エージェントのプロンプトやモデルの変更を昇格させるのにどれくらいの時間がかかりますか。そして、それが安全だと判断する根拠は何でしょうか。
